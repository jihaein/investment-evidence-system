# 급락 모델 운영: 검색 결과 크롤링 → 네이버 검색 API 전환 설계

작성 2026-11-18. 상태: 설계(구현 전). 대상: `models/sudden/live.py`의 매일 실행(평일 18:30).

## 1. 왜 바꾸나

지금 운영은 백테스트와 같은 방식으로 **네이버 뉴스 검색 결과 페이지를 날짜별로 긁는다**(`crawl_plan.py` + `naver_crawl.py`).

| 문제 | 실제로 일어난 일 |
|---|---|
| 차단 | 2026-11-18 요청이 빨라지자 검색이 403으로 막혀 1시간 넘게 멈췄다 |
| 페이지 구조 변경 | 외부 언론사 HTML 하나 때문에 수집이 2시간 같은 자리에서 멈췄다(11-18) |
| 양 | 하루치를 돌려도 평소 기사(180일)를 날짜별로 다시 검색한다. 사건이 많은 날은 수백~수천 번 검색 |
| 약관 | 검색 결과 페이지 자동 수집은 공식 경로가 아니다 |

실제 서비스로는 **공식 API로 매일 받아 쌓는 방식**이어야 한다. 설계서 v3.1 6절("운영용 뉴스는 검색 API를 매일 받아 쌓는다")과도 맞다.

## 2. 출처별 역할

| 출처 | 쓰는 곳 | 비고 |
|---|---|---|
| **네이버 검색 API (뉴스)** | 기사 목록(제목·요약·링크·게시 시각) | 공식. 키 필요. 최신순 정렬 가능, **날짜 지정 검색은 안 됨** |
| 기사 본문 페이지 | 판정에 쓸 본문 | 제목에 회사명이 있는 기사만, 하루 수십 건 수준 |
| OpenDART API | 필수 공시 단위, 실적 공시 | 지금과 같음 |
| KRX 시세 (pykrx) | 급락 감지, 시장 규칙 | 지금과 같음 |
| 크롤링 캐시 | 과거 백테스트·파이널, 운영 초기의 평소 기사 | 운영 경로에서는 더 이상 새로 긁지 않음 |

**발급처는 네이버 클라우드 플랫폼의 NAVER API HUB다** (2026-11-18 확인). 검색 API는 개발자센터에서 API HUB로 옮겨 가는 중이고, 개발자센터 키로는 API HUB를 호출할 수 없다.

| 항목 | 값 (NCP 공식 문서) |
|---|---|
| 호출 주소 | `GET https://naverapihub.apigw.ntruss.com/search/v1/news` |
| 헤더 | `X-NCP-APIGW-API-KEY-ID` (Client ID), `X-NCP-APIGW-API-KEY` (Client Secret) |
| 파라미터 | `query`(필수), `display` 1~100, `start` 1~1000, `sort` `sim`·`date`, `format` `json` |
| 응답 항목 | `title`, `originallink`, `link`(네이버 뉴스 주소, 없으면 원문), `description`, `pubDate` |
| 한도 | 하루 25,000회. 초과하면 429 |
| 요금 | 종량제. 문서상 현재 한시 무료이고 유료 전환 때 공지. 콘솔에서 이용 한도·임계치 알림을 설정해 둔다 |

출처: [뉴스 검색 API 문서](https://api.ncloud-docs.com/docs/naver-api-hub-search-news), [개발자센터 → API HUB 이관 가이드](https://guide.ncloud-docs.com/docs/apihub-migration), [API HUB 개요](https://api.ncloud-docs.com/docs/naver-api-hub-overview).

## 3. 매일 흐름 (평일 18:30)

```
1. prices    KRX 시세 (지금과 같음)
2. news      [새] 관심 종목 전체의 최신 기사 목록을 API로 받아 쌓는다 (급락이 없는 날도 한다)
3. events    급락 감지 (지금과 같음)
4. names     이름 보정 (지금과 같음)
5. bodies    [새] 그날 급락 사건의 뉴스 창 기사 중 제목에 회사명이 있는 것만 본문을 받는다
6. np        N·P 점수 (지금과 같음, 쌓인 기사로 계산)
7. dart      공시 (지금과 같음)
8. ach       판정 (파이널 설정 그대로)
9. export    결과 파일
```

바뀌는 것은 지금의 `crawl` 단계(검색 결과 크롤링)가 `news`(목록 쌓기)와 `bodies`(본문 일부)로 나뉘는 것뿐이다. 3·4·6~9단계는 그대로 둔다.

## 4. 기사 목록 받기 (`news` 단계, 새 파일 `news_api.py`)

- **대상 종목:** 보통주, 시가총액 1,000억 이상(2026-11-16 기준 1,241종목). 서비스에서는 사용자 보유 종목을 더한다.
- **요청:** 종목마다 회사명(이름표의 모든 이름)을 따옴표로 감싸 검색, `sort=date`, `display=100`.
- **페이지 넘김 멈춤 규칙:** 마지막으로 받은 시각보다 오래된 기사가 나오면 멈춘다(매일 실행하므로 보통 1~2번 요청). 처음 실행이거나 오래 쉬었으면 시작 위치 한도(1,000)까지.
- **호출량 어림:** 1,241종목 × 평균 1.5회 ≈ 1,900회/일. 기사가 많은 대형주 일부가 10회까지 써도 한도 안이다.
- **저장:** 지금 판정 단계가 읽는 `crawl.sqlite3`와 **같은 형식**으로 쓴다. 그래서 `news_review`·`np_batch`·`p_pool`·`ach`를 고치지 않는다.
  - `searches`: (종목, 게시일, 검색어)마다 한 줄. 결과 목록에 제목·링크·게시 시각을 넣고 상태는 `complete`(API로 받은 날은 그날 기사가 없어도 `empty`로 적어 "수집 완료"를 표시)
  - `articles`: 본문을 받은 기사만(5절)
  - 출처 표시: `source: "naver_api"`
- **회사명 확인:** 제목 매칭은 엄격 매칭(`news_review.name_in`)을 그대로 쓴다.

## 5. 본문 받기 (`bodies` 단계)

- 대상: 그날 급락 사건의 **뉴스 창**(D-2 세션 ~ D 15:30) 기사 중 제목에 회사명이 있는 것.
- 네이버 뉴스 링크(`n.news.naver.com`)는 지금 파서(`naver_crawl.parse_article`), 언론사 원문은 `external_article`.
- 하루 상한(예: 300건)과 요청 간격(6초)을 둔다. 실패한 기사는 그 기사만 실패로 적고 계속한다.
- **본문 없이도 판정하는 길(검토):** API 요약(description)만으로 단위 분류가 되는지 지난 사건으로 비교한다. 되면 본문 요청을 더 줄인다.

## 6. 평소 기사(N·P 기준)를 어떻게 채우나

N은 앞 180일, P는 앞 90일 기사와 비교한다. API는 과거 날짜를 골라 검색할 수 없으므로 **매일 받은 목록을 계속 쌓아서** 쓴다.

| 시기 | 평소 기사 출처 |
|---|---|
| 전환 직후 | 지금까지의 크롤링 캐시(`cache/naver_live`, `cache/naver_120`)를 같은 DB로 합친다. 첫 실행에서 시작 위치 한도(1,000)까지 받아 최근 기사를 채운다 |
| 6개월 뒤 | API로 쌓은 기사만으로 180일이 찬다 |

- 쌓이지 않은 종목·기간은 지금처럼 `collection_incomplete`(판정 보류)로 처리된다. 숫자를 지어내지 않는다.
- P는 이미 여러 종목을 합친 기준 분포를 쓰므로(`p_pool`) 종목 하나의 이력이 짧아도 계산된다.

## 7. 시간 경계

- 판단 시각은 지금과 같이 급락일 15:30. API의 게시 시각(pubDate, +09:00)으로 뉴스 창을 자른다.
- API는 수정 시각을 주지 않는다. 본문을 받은 기사만 기사 페이지의 수정 시각으로 `modified_after_decision`을 표시한다(지금과 같은 규칙).
- 18:30에 실행하므로 15:30 이후 기사도 목록에 들어오지만, 판정에는 쓰지 않는다(지금과 같음).

## 8. 실패와 한도

| 상황 | 처리 |
|---|---|
| 일시 오류(5xx, 연결 끊김) | 30초 → 2분 → 10분 간격으로 3번 다시 |
| 호출 한도 초과 | 그날 남은 종목은 다음 날 이어서 받는다. `run_status.json`에 `quota_exceeded`와 못 받은 종목 수 |
| 키 없음·잘못됨 | 바로 멈추고 상태 파일에 적는다(크롤링으로 자동 대체하지 않음) |
| 본문 실패 | 그 기사만 실패. 판정은 받은 본문으로 한다 |

키는 `.env`의 `NAVER_API_HUB_CLIENT_ID`, `NAVER_API_HUB_CLIENT_SECRET`(사람이 직접 넣는다). 로그·결과에 키 값을 쓰지 않는다.
유료 전환에 대비해 NCP 콘솔(Application → 이용 한도 설정)에서 하루 한도를 정해 둔다.

## 9. 백테스트와의 관계

- 과거 표본(2016~2019, 2023~2025, 2026 검증)과 **120종목 2020~2026 파이널**은 지금 수집한 크롤링 데이터로 끝낸다. 파이널 설정은 바꾸지 않는다.
- 운영 경로만 API로 바뀐다. 그래서 "백테스트 때와 다른 경로로 기사를 모은다"는 차이가 생긴다. 아래 병행 검증으로 차이를 잰다.

## 10. 전환 전 검증 (병행 운영 2주)

같은 날을 두 방식으로 돌려 비교한다. 크롤링은 이 기간에만 하루치 사건 창만 돌린다.

| 지표 | 통과 기준 |
|---|---|
| 사건 창의 회사 기사(제목에 회사명) 재현율: API 목록 ÷ 크롤링 목록 | 0.9 이상 |
| 판정이 같은 사건 비율 | 0.8 이상 (다르면 원인 기사를 사례로 기록) |
| 하루 API 호출 수 | 한도의 50% 이하 |
| 실행 시간 | 1시간 이내 |

통과하면 크롤링 경로를 운영에서 뺀다(코드는 백테스트용으로 남긴다).

## 12. 필요한 것과 열린 질문

- **필요:** 네이버 클라우드 플랫폼 콘솔 → NAVER API HUB 이용 신청 → Application 등록(검색 API) → Client ID·Secret을 `.env`에 직접 입력.
- **열린 질문**
  1. 관심 종목 범위: 시가총액 1,000억 이상 전체로 할지, 서비스 사용자 보유 종목만 할지(호출량과 평소 기사 품질이 달라진다).
  2. 본문 없이 요약만으로 판정할지(5절 비교 결과로 정한다).
  3. 서비스 규모가 커지면 유료 뉴스 피드나 빅카인즈 계약으로 옮길지.
